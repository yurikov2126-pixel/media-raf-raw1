# МЧС: переход от изолированных тестов к штатному эфиру

## Цель

Штатный режим не должен требовать ни галочек «Принимать Android-события
изолированно» / «Аппаратное испытание GPIO13», ни фраз `ISOLATED` и
`ISOLATED RELAY`. Источник управления — центральная служба событий,
а Windows Agent — штатный аппаратный исполнитель. Один eventId соединяет
все выходы.

## Production-цепочка (целевое поведение)

1. Android ingest принимает только `MISSILE_DANGER` и
   `MISSILE_ALL_CLEAR` по настроенному каналу. Сохраняется дедупликация,
   проверка актуальности и журнал.
2. Сервер связывает событие с назначенным ALARM/ALL-CLEAR и повторами.
   Оповещения имеют приоритет над AutoDJ, сеткой и прямым эфиром.
3. Radio Worker прерывает обычный эфир и передаёт файл в основной
   публичный маршрут `/radio/live` с естественным окончанием и возвратом.
4. Windows Agent получает ту же event-bound команду. Для физического
   выхода перед звуком нужен подписанный ON от ESP32, минимум 3 сек
   прогрева с актуальным lease и независимой проверкой аппаратной
   готовности; затем играет WAV до конца.
5. После полного завершения каждого сообщения Agent возвращает источник
   и отдаёт управление реле штатной политике; журналы Worker и Agent
   показывают совпадающий eventId и завершение. Между сообщениями
   нельзя допускать непредусмотренных щелчков реле.
6. Сервер отображает состояние двух аудиовыходов и ESP32 отдельно.
   Отсутствие подтверждения не записывается как успех.

## Текущее состояние и блокеры

**Этот PR не включает передачу тревоги в публичный эфир и не включает реле.**
Он добавляет только общий серверный контракт `assessMchsProductionReadiness`,
который не использует слова `ISOLATED` и не зависит от GUI-галочек.

Текущие `runMchsTwoChannelExecution` и
`dispatchIsolatedMchsEvent` выполняют только изолированные сценарии,
запрещают `publicStreamAllowed` и `amplifierAllowed`.
Нельзя «включить prod» удалением защитной проверки: нужен отдельный
реальный маршрут Worker/Agent с согласованным жизненным циклом.

Недостаточно доказано:
- непрерывная работа физического усилителя AA-300: наблюдались OFF/ON
  во время тестирования, причина середины сообщения ещё не исключена;
- устойчивость серверного `/agent/amplifier-intent`: наблюдались HTTP 502
  и URLError;
- подтверждённая аппаратная готовность, а не только `ON_COMMANDED`;
- реальное прерывание публичного потока при Android-событии.

## Этап после PR #996 — модель приоритетной сессии

В `server/src/lib/mchsStationPrioritySession.js` добавлена независимая
модель штатного приоритетного источника Worker:

`PREEMPTING → PLAYING → RESUMING → COMPLETE`.

- `PREEMPTING` требует подтверждения прекращения обычного источника,
  не просто принятия HTTP-запроса.
- `PLAYING` завершается успешно только при `FILE_COMPLETED` и
  точном количестве повторов; никакого штатного STOP.
- `RESUMING` требует фактического подтверждения возвращения звука
  обычной программы.
- Ошибки и отмены завершаются `FAILED`, без ложного COMPLETE.
- Повторное использование eventId запрещено и после завершения.
- Модель **пока не подключена к live Worker** и не отправляет команд
  включения усилителя или событий в публичный эфир. Сначала надо
  адаптировать PCM-аудио маршрутизацию и документировать инварианты,
  только потом соединить её с основным Worker.

## Интеграция PCM Radio Worker (PR #998)

Следующий этап подключает `mchsStationPrioritySession` к реальным PCM-кадрам
единого Worker-энкодера через `mchsWorkerPcmEvidence`. Он наблюдает
существующий `trainingOverlay.replace(frame)` и получает событие начала
только после передачи кадра из выбранного приоритетного источника:

- `PREEMPTING → PLAYING`: аудиофрейм действительно заменён PCM оповещения.
- `PLAYING → RESUMING`: последний PCM-фрейм доигран с точным числом
  повторов и `FILE_COMPLETED`, а не просто получен HTTP START.
- `RESUMING → COMPLETE`: после оповещения в тот же энкодер поступил
  следующий ненулевой PCM-фрейм обычной программы. Тишина не считается
  подтверждением успешного восстановления.
- STOP и ошибки источника завершают запись FAILED.

Доказательства доступны во внутреннем авторизованном GET
`/mchs-training-stream` как `priorityPcmEvidence`; сетевые
эндпоинты старта, Android-ingest и управление ESP32 **не меняются**.
Эта телеметрия пока использует существующий учебный overlay и
только готовит основу для полноценного штатного источника МЧС.

Подтверждение передачи PCM на вход encoder **не доказывает** фактическую
слышимость в браузере или через усилитель; это отдельные проверки.

## Порядок реализации

1. Доработать эфирный Worker: отдельная приоритетная event-bound сессия
   `MCHS_PRODUCTION`, без искусственного STOP при естественном окончании.
2. Доработать Agent и GPIO13: единственный владелец power-lease,
   подготовка до старта WAV, наблюдение непрерывности, OFF/ON по ясному
   контракту. Запретить несовместимые параллельные power-команды.
3. Подключить ingestion Android к единому координатору Worker/Agent
   только после интеграционных тестов обеих веток и проверенного
   возврата штатного вещания.
4. Заменить тестовые чекбоксы и фразы в штатном интерфейсе на
   постоянный статус «Система экстренного оповещения» и отдельный
   безопасный режим диагностики без физического вывода.
5. Выполнить аппаратную приёмку электросхемы и тесты с физически
   отключёнными линиями PA, затем отдельную проверку слышимости
   в контролируемом месте до допуска ко всей системе колледжа.

Ни один вывод `ready` из read-only readiness не даёт право отправить
команды ON/START — решение о выходе из HOLD должно принимать реально
реализованное управляющее средство после подтверждения безопасности.
