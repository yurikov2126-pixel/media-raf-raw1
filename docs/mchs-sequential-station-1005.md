# PR #1005 — последовательная доставка ALARM → ALL-CLEAR

В исходной реализации #1001–#1004 каждый новый Android event немедленно отправлялся в Worker. Если предыдущий ALARM ещё звучал, внутренний POST возвращал 409 `STATION_SOURCE_BUSY`; никакой сериализации и повтора такой команды не было.

Теперь сервер использует уже существующий PostgreSQL ledger `mchs_android_execution_intents_v1` как очередь событий. Новые уведомления, прошедшие действующую проверку типа, региона, возраста и ALARM-привязки, получают `occurredAt` исходного Android события.

Цикл монитора каждые 15 секунд сначала читает внутренний `GET /mchs-station-session`, а затем под PostgreSQL advisory lock `741581453` выбирает **одну** самую раннюю свежую запись. `PLAYING`, `PREEMPTING`, `RESUMING`, занятая подготовка или нездоровый терминальный журнал блокируют допуск следующего START. Перед сетевой отправкой транзакция помечает выбранное событие `DISPATCHING`, чтобы другой процесс не отправил тот же eventId параллельно.

После ответа START статус становится `START_ACCEPTED`, `QUEUED` (только для 409 `STATION_SOURCE_BUSY`) или `START_REJECTED`. Переход в `QUEUED` не создаёт ошибочный финальный receipt; следующий тик повторно рассматривает этот же eventId. Естественное завершение WAV не создаёт STOP. При рестарте API уже `DISPATCHING` событие не воспроизводится повторно вслепую: результат потенциально неопределён.

## Существенные ограничения

- Действующий контракт Worker принимает `occurredAt` не старше **120 секунд**. Если короткие/длинные сообщения и ожидание в очереди превысят это окно, событие будет помечено `EXPIRED`, а не проиграно. Это временный недостаток, который необходимо решить отдельной проверяемой схемой допуска на момент поступления уведомления — без фальсификации времени. Поэтому данный PR **не гарантирует** воспроизведение любого отбоя после длительного ALARM.
- При аварии API после отправки START, но до записи результата, `DISPATCHING` не возобновляется автоматически. Потребуется reconcile с терминальным журналом Worker и политика `UNKNOWN`.
- Не изменены ни Windows Agent, ни GPIO13/ESP32, ни маршрутизация реального усилителя. Сами production флаги остаются выключенными по умолчанию. PCM-подтверждение энкодера не гарантирует фактическую слышимость в кабинетах.
- Для продолжительной работы нескольких API процессов общий PostgreSQL advisory lock защищает выбор, но полный transactional outbox и подтверждение межканального исполнения пока не реализованы.

## Проверки

Тесты проверяют ALARM → ALL-CLEAR, BUSY→QUEUED, отсутствие повторного запуска уже занятого `DISPATCHING`, истечение 120 секунд, ошибку/недоступность Worker и отсутствие ложного результата `COMPLETE`.
