# Реальная тревога и силовая цепь AA-300 — этап 1033

Проблема: при настоящем ALARM и ALL-CLEAR звук был слышен в Windows Agent, но PA-усилитель оставался выключен. Ранее Agent записывал eventId в INTENT_RESPONSE, но старый санитарный фильтр удалял его при отправке в API. Поэтому хронология реле в админке не позволяла уверенно сопоставить команды с конкретным оповещением.

## Исправления

- Agent теперь отправляет в защищённой диагностической телеметрии только идентификатор события с допустимыми символами `[A-Za-z0-9_-]` (1–128), без текста уведомления, токенов, ключей, URL и сырых ошибок.
- Сервер принимает и сохраняет eventId только вместе с подтверждённой авторизацией конкретного Windows Agent и ESP32, соблюдая существующий предел свежести и количество записей. `INTENT_RESPONSE`, `POWER_COMMAND`, `RELAY_TRANSITION` и `POWER_ERROR` смогут относиться к одному реальному ALARM.
- Agent требует, чтобы ответ `POST /power` совпадал с запрошенной командой: `ON_COMMANDED` для ON и `OFF_COMMANDED` для OFF. `ok:true` без ожидаемого `amplifierPower` больше **не считается** подтверждением выполнения. В случае несовпадения событие `POWER_ERROR` будет отражено в диагностике.
- Это подтверждение состояния команды контроллера, **не измерение напряжения 220 В и не доказательство звучания PA**.

## Что осталось неизменным

Нет нового способа включать GPIO13, не меняется разрешение AUTO/MANUAL, не отключаются локальный аппаратный допуск, emergency OFF, watchdog и аренда, не добавляются тестовые Android-события, не изменяется задержка основного ALARM. Изменения в Windows Agent требуют нового EXE для использования на производственном ноутбуке.

## Последующая проверка

На следующем легитимном событии отслеживать совпадение `eventId` между запросом разрешения питания, командой и результатом ESP32; отдельно проверить, была ли реально включена силовая цепь и слышен PA. Не синтезировать сигнал тревоги в основном эфире ради теста. До подтверждения штатные средства оповещения являются основными.
