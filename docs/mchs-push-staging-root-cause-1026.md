# PR #1026 — исправление отсутствия PUSH при настоящем Android-оповещении

## Подтверждённые дефекты PR #1024

В `POST /api/safety-ingest/event` обработчик успешно сохранял `SafetyMchsEvent`, но Prisma `upsert(...select)` возвращал только `id`, `receivedAt`, `verified`. Позже тот же обработчик проверял `event.eventType===pushCandidate.type`. Так как `eventType` отсутствовал в выбранном объекте, проверка всегда была ложной, и **ни одна запись `SafetyMchsPushDelivery` не создавалась**. Поэтому фоновая рассылка не могла появиться в `MCHS_PUSH_DELIVERY`.

Дополнительно ветка PUSH не должна требовать `SafetyMchsEvent.verified=true` для опасности БПЛА: это поле относится к *допуску звуковой ракетной очереди*, а не к проверенной HMAC-доставке Android. Два БПЛА-события намеренно не получают аудиодопуск.

## Изменения

- `eventType:true` включён в `select` при сохранении принятого Android-события.
- Отдельная тестируемая функция `shouldStageMchsPushDelivery` проверяет: сообщение прошло существующую HMAC-авторизацию (вызывается только внутри подписанного маршрута), классификация и регион/канал/время прошли PUSH-фильтр, это **новое** событие, и тип сохранённой записи совпадает с типом PUSH.
- PUSH теперь не зависит от `verified` (это поле ограничивает только запуск ALARM/ALL-CLEAR).
- Сохраняются транзакция, уникальность eventId, двухминутный срок, Web Push/FCM, защита от повторной отправки, прежняя звуковая цепочка.
- Добавлены тесты, включая регрессию обязательного поля Prisma `select`, новое/повторное событие и БПЛА без звукового допуска.

## После объединения

Не нужно повторять прошедшую настоящую тревогу: PR намеренно не добавляет PUSH к историческим сообщениям и не рассылает их повторно. При следующем допустимом уведомлении должна появиться запись в `SafetyMchsPushDelivery`, затем лог `MCHS_PUSH_DELIVERY`.

Если запись есть, но `webSent=0` и `mobileSent=0`, отдельно проверяются текущие VAPID/FCM конфигурация и подписки. Проверка может выполняться по агрегированным диагностическим результатам без разглашения секретов, токенов и содержимого личных уведомлений.

Изменения не включают/выключают радио или GPIO13. Ремонт аппаратного запроса питания оформлен отдельно в PR #1025.
