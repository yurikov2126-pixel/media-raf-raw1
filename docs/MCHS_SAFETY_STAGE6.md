# МЧС: этап 6 — надёжность подтверждения доставки (подготовка)

Изменения усиливают контракт между тестовым отправителем (этап 5) и тестовым API (этап 3).

- Сервер в успешном ответе /api/safety-ingest/event возвращает тот же `eventId`, что присутствовал в подписанном запросе.
- Агент помечает SQLite-запись доставленной только при **HTTP 200 + accepted=true + точном совпадении eventId + testOnly=true**.
- Некорректный JSON, массивы вместо объектов, вложенные значения вместо текстовых полей и невозможные значения времени не приводят к ошибочной постановке событий в очередь.
- stderr ADB-процесса перенаправлен в DEVNULL, чтобы не блокировать stdout при переполнении stderr pipe.
- Добавлены базовые unit tests на недоверенные payload.

## Обязательно до merge
Проверить `python3 -m unittest discover -s tools/mchs-sender -p 'test_*.py'`, подпись/дедупликацию через preview API, временную недоступность API и рестарт systemd. Нельзя направлять отправитель на продакшен или включать эфир.

## Оставшиеся ограничения
Android Bridge мог писать лог в другом фактическом формате: тестировать на настоящем MCHS Bridge без подмены уведомлений. Logcat не гарантирует полную или непрерывную доставку, поэтому агента нельзя считать надёжной системой экстренных сообщений. Нет Android persistent queue, нет подтверждённой доставки FCM, нет подтверждения подлинности сообщения МЧС и нет функции аварийного вещания.
