# Радио 2.0: переход на серверный эфир, локальный резерв

## Целевая архитектура
Сервер Ubuntu 24.04 + aaPanel: **единый плейаут по московской сетке** → серверный PCM/AAC/Opus кодер → непрерывный радиопоток → Radio Agent на Mac/Windows → тестовый аудиовыход (после отдельного допуска — колледжная система).
Удалённая эфирная студия (WebRTC с телефона) переключается на серверном аудиомикшере, **не** на Mac. Без активной студии в основной поток идёт музыка/записи из расписания.
На клиенте держим заранее скачанный и проверенный кэш утверждённых передач. Если **нет основного потока** или закончилась допустимая задержка/heartbeat, клиент включает локальное резервное воспроизведение **с текущей позиции общего курсора**, пропуская законченные дорожки; назад в начало передачи не возвращается.
Когда серверный поток стабильно восстановился (несколько секунд подтверждённого декодируемого звука), агент переключается на него с коротким fade, резерв выключается. Не допускается одновременный вывод двух источников.

## Сейчас реализовано этим PR
- `GET /api/radio-agent/agent/now-playing` (Bearer token радиоустройства) возвращает `cursor.status`, `slot`, `track.id`, `offsetMs`, `at`; время абсолютное UTC, редакторские даты — Europe/Moscow.
- Вспомогательная функция `resolveRadioCursor` вычисляет текущий трек и позицию из утверждённой сетки и длительностей аудиофайлов. Никаких изменений текущего проигрывателя и действующего прямого эфира нет.
- Тесты точных границ, середины дорожки, конца слота и отсутствия зацикливания.

**Это фундамент, а НЕ работающий поток и НЕ автоматический резерв.** Не подключать к усилителю.

## Следующие PR по порядку
1. Сервис playout на сервере (отдельный systemd worker), одиночный мастер-таймлайн, очередь источников; FFmpeg уже доступен как `ffprobe`, но отдельно проверять `ffmpeg`. Изоляция ресурсоёмкого кодирования от основного Express API. Добавить мониторинг ошибок, часы, рестарт.
2. Стриминг с контролем доступов: схема primary может быть Opus по WebRTC для малой задержки либо совместимый AAC/HTTP(S) с буфером. Выбрать после замера сети/задержки; запретить публичный бесконтрольный аудиоendpoint с токеном в query string. Для масштабирования и сложных NAT — TURN; при необходимости отдельный streaming proxy.
3. Приём/декодирование основного потока Mac и Windows: готовность только после реальных аудиофреймов, таймауты, backoff, метрики jitter, логи.
4. Общий арбитр выходного устройства: PRIMARY_STREAM → LOCAL_FALLBACK → SILENCE; локальный резерв использует `now-playing`/последнюю синхронизированную сетку и точный offset трека, а не флаг `played.json`. Fade, защита от потока без слышимого звука, без наложения.
5. Вмешательство студии и приоритеты: студия переключается на **сервере**, а не локально. Источник меняется один раз для всех. Экстренное оповещение — **независимый аппаратный приоритет**, никогда не зависит от Интернета или этого приложения.
6. Длительные испытания с отключением Wi-Fi, серверного worker, iPhone/PWA, переходом прямой эфир/плейлист, перегревом/перезагрузкой и часами UTC+3. Лишь затем тест подключения колледжной акустики под контролем ответственного сотрудника.

## API пример
```json
{
  "timezone": "Europe/Moscow",
  "cursor": {
    "status": "SCHEDULED",
    "at": "2026-10-17T12:01:30.000Z",
    "slot": {"id":"...","playlistId":"...","name":"...","startAt":"...","endAt":"..."},
    "track": {"id":"...","name":"...","offsetMs":30000,"durationMs":120000,"index":1}
  }
}
```

## Запуск / deploy
- Изменения только серверные: `radioAgent.js`, `radioTimeline.js`, тестовый файл; новых npm/apt-пакетов и Prisma-миграций **нет**. Ubuntu 24.04 + aaPanel: штатный deploy Node API (`mediaraf-api.service`).
- Локально серверные тесты: `cd server && npm test -- radioTimeline` (использовать установленный репозиторный npm lockfile).
- Mac/Windows: ничего обновлять для этого PR не нужно. Устройства продолжат текущую экспериментальную логику, пока отдельные стриминг/резерв PR не будут внедрены.
