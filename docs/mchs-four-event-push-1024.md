# PR #1024 — PUSH по четырём типам уведомлений Android

## Назначение

Платформа уже получает HMAC-подписанные события от отдельной Android VM, имеет Web Push подписки (PWA) и Android FCM через `MobilePushToken`. Новых шлюзов, новых Android-приложений и ручного запуска не требуется.

При первом сохранении допустимого уведомления из разрешённого Android-канала Тульской области независимо от Radio Worker формируется PUSH на все подписанные браузеры и все зарегистрированные Android-клиенты:

| Событие | PUSH | Звук основного эфира |
| --- | --- | --- |
| Опасность атаки БПЛА | Да | Нет |
| Отбой опасности атаки БПЛА | Да | Нет |
| Ракетная опасность | Да | Да, существующий ALARM × 2 |
| Отбой ракетной опасности | Да | Да, существующий ALL-CLEAR × 1 |

Настроенное число повторений ракетной опасности берётся из текущих настроек, не захардкожено в PUSH.

## Безопасность и дедупликация

PUSH допускается только после существующей HMAC-проверки запроса, классификации в один из четырёх типов, совпадения `channelId` с `MCHS_MISSILE_TRUSTED_CHANNEL_IDS`, региона «Тульская область» и актуальности `occurredAt` (не старше 120 секунд, не более 30 секунд в будущем). Другие виды сообщений и искусственные `/diagnostic` не рассылаются.

Новое событие и его PUSH-задание создаются в одной транзакции, с уникальным `eventId`. Повторная отправка Android POST не создаёт второе PUSH-задание. Существующие исторические записи не переигрываются при развёртывании. Отдельная таблица `SafetyMchsPushDelivery` хранит состояния `PENDING/SENDING/SENT/NO_SUBSCRIBERS/FAILED/EXPIRED` и счётчики отправленных Web/FCM сообщений.

Фоновый исполнитель проверяет очередь каждые 5 секунд и сразу при поступлении события, ограничивает Web Push TTL двумя минутами (вместо обычных суток). Android FCM получает высокий приоритет и срок жизни 120 секунд. Отправки после истечения срока актуальности не начинаются. Перед отправкой заявка атомарно переходит в `SENDING`: после падения процесса неопределённая отправка **не повторяется автоматически**, чтобы не дублировать тревогу. Это режим предпочтения недублирования; он означает, что при падении API во время рассылки некоторым подписчикам PUSH может не поступить.

В логах `MCHS_PUSH_DELIVERY` — тип, ID и числа успешных Web Push / Android FCM отправок; никаких секретов или токенов.

Тело PUSH использует короткий текст, сохранённый из Android, без утверждения о независимой официальной аттестации. Ссылка ведёт в существующее приложение (`/app`); Web Push для опасности просит взаимодействия пользователя. Наличие подтверждения поставщика PUSH не является гарантией, что экран каждого телефона показал сообщение.

## Развёртывание

1. Применить новую Prisma-миграцию. Повторного развертывания Android-моста и Windows Agent не требуется.
2. Перезапустить API обычным production-deploy; Web Push использует существующие `VAPID_PUBLIC_KEY/VAPID_PRIVATE_KEY` и браузерные подписки.
3. Для нативного Android PUSH нужны уже существующие `MOBILE_PUSH_ENABLED=true` и рабочие настройки Firebase; если мобильный канал выключен, Web Push работает независимо.
4. Не меняйте `MCHS_ANDROID_MAIN_STATION_DISPATCH_ENABLED`, `RADIO_MCHS_STATION_COMMANDS_ENABLED` и `MCHS_MAIN_STATION_COORDINATOR_ENABLED`: PUSH обрабатывается отдельно, звуковая цепочка остаётся прежней.
5. В логах после настоящего подходящего уведомления должны появляться `MCHS_PUSH_DELIVERY` и счётчики по каналам. Не генерируйте искусственные сообщения об опасности через production-приёмник ради проверки.

## Ограничения

- PUSH получат устройства, зарегистрировавшие подписку/FCM-токен в платформе и имеющие разрешение ОС на уведомления. Системный PUSH не гарантирован при отсутствии сети, отключённых уведомлениях или сбое push-провайдера.
- PUSH не заменяет штатные сертифицированные средства экстренного оповещения колледжа.
- Изменения не касаются реле ESP32, усилителя AA-300, расписания радио, подтверждения подлинности МЧС или поведения звуковых ALARM/ALL-CLEAR.
