# PR #1014 — согласованная запись телеметрии ESP32 и подтверждение диагностических каналов

## Исправленная гонка

До этой версии `POST /api/radio-agent/agent/esp32-status` сначала читал значение `radio_esp32_status_v1` вне транзакции и отдельно сохранял его, а затем запускал транзакцию с блокировкой для `mchs_esp32_transition_evidence_v1`. При одновременных запросах из Agent старый снимок мог перезаписать новый. При ошибке сохранения журнала ответ мог содержать `ok:true`, хотя события не были записаны.

Теперь обе настройки PostgreSQL обрабатываются **в одной транзакции**, защищённой существующей `pg_advisory_xact_lock(741581454)`. Внутри неё последовательно:
1. Читаются предыдущие снимки и журнал;
2. Выполняется сравнение firmware-событий и фильтрация журнала Windows Agent;
3. Записываются и последний снимок ESP32, и общий журнал переходов;
4. Возвращается успешный ответ только после commit.

Если транзакция не удалась, API отдаёт ошибку, поэтому Agent может повторить отчёт. Системный relay policy, GPIO13, HMAC и watchdog не меняются.

## Новые признаки для административной вкладки

Снимок содержит два независимых факта:
- `firmwareHistoryReported`: последнее сообщение содержит **валидную** по формату последовательность `relayTransitionHistory` из новой ESP32-прошивки;
- `agentPowerEvidenceReported`: Agent использует новый протокол передачи диагностических решений, включая корректный пустой массив, когда переключений не было.

Флаги показывают поддержку и **получение протокола**, а не наличие физических включений. Старое firmware, старый Agent и недействительные данные не должны выглядеть как обновлённая диагностика.

`GET /api/safety/missile-main-station-readiness` возвращает эти сведения в существующем блоке `esp32`; вкладка «Тракт оповещения» выводит их отдельно. Признаки `readyForLivePA:false` и `physicalOutputConfirmed:false` остаются неизменными.

## Ограничения

- Нельзя подтвердить физическое питание AA-300 без независимого измерения напряжения; GPIO13 — только командное состояние.
- Нельзя определить доставку звука по признакам получения JSON.
- Для получения новых данных требуется актуальная ESP32-прошивка из PR #1013 и Windows Agent с передачей power evidence из PR #1012, реально работающие в локальной сети.
- Пока административный маршрут использует прежнюю привязку `MCHS_AGENT_LAB_DEVICE_ID`. Перенос на production-привязку — отдельная миграция конфигурации, здесь не меняется, чтобы не перестать показывать ранее привязанное устройство.
- Никаких автоматических МЧС-тревог и управления силовой цепью PR не активирует.

Тесты покрывают новую/старую прошивку, пустую диагностическую партию Agent, недопустимые записи и запрет ложного разрешения громкоговорителей. CI также продолжает собирать ESP32 и Windows Agent.
