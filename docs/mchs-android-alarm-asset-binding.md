# Android МЧС → медиа ALARM: автоматическая привязка без публичного запуска

Этот этап устраняет разрыв между полученным Android push и конкретным файлом
`ALARM`, который должен воспроизводиться в дальнейшем. Этап **не** даёт
Android-приложению полномочий запускать публичное радио и громкоговорители.

## Действующий поток

1. Существующий защищённый ingest сохраняет Android-сообщение в БД.
2. Планировщик `tickMchsAndroidMonitor` раз в 15 секунд выявляет новые
   уведомления и сверяет их с настройками `mchs_four_type_rules_v1`.
3. Для свежего подтверждённого наблюдения подходящего типа и региона ищется
   реально существующий файл `radioAsset` категории `ALARM` с
   корректным MIME и положительной длительностью.
4. Сохраняется одно предложение `STAGED` на `sourceEventId`: тип,
   `assetId`, число повторов, ожидаемая длительность. Для отбоя
   число повторов всегда 1.
5. При повторной доставке `sourceEventId` предложение не дублируется.
6. Администратор видит привязку и причины отказов через защищённый,
   **только читающий** GET `/api/safety/android-alarm-bindings`.

## Что НЕ изменилось

- Нет вызова `/mchs-training-stream` из обработчика Android.
- Нет автоматического START в Worker, Agent, PA или на `/radio/live`.
- `officialSourceVerified=false`, `dispatchAuthorized=false`.
- Промежуточные данные из приложения не равнозначны независимо
  аттестованному источнику официального предупреждения.
- Блокировки реального запуска и возможность аварийного останова
  сохранены как прежде.

## Регрессионные проверки

```sh
cd server
node --test tests/mchsAndroidAlarmBinding.test.js \
  tests/mchsAndroidObservationMonitor.test.js \
  tests/mchsAndroidIntentLedger.test.js
```

Для дальнейшего ввода в эксплуатацию остаётся подтвердить источник
предупреждений, связать согласованную команду с аудио на обоих выходах
и провести контролируемое учебное испытание. Отсутствие ручного START/STOP
в нормальном процессе не исключает техническую возможность прервать
ложное или зациклившееся оповещение.
