# PR #1011 — история отдельных командных переключений GPIO13

## Зачем это нужно

В предыдущей телеметрии были лишь `relayOffTransitions` и `lastRelayOffReason`. Если два или более выключения случались между опросами Windows Agent, первый счётчик фиксировал **число** OFF, но ранние **причины** терялись. Именно такой короткий цикл мог наблюдаться в работе AA-300.

## Что добавлено

ESP32 хранит в оперативной памяти последние **12 командных переключений GPIO13** в кольцевом буфере с фиксированным размером. Каждое событие имеет:
- `seq` — последовательный номер в пределах одного `bootNonce`;
- `uptimeMs` — монотонное время `millis()` с момента запуска;
- `on` — новое командное состояние GPIO13;
- `reason` — причина (например `HEARTBEAT_TIMEOUT`, `POWER_LEASE_EXPIRED`, `WIFI_LOST`, `SIGNED_PERMIT_FALSE`).

`GET /health` возвращает `relayTransitionSequence` и `relayTransitionHistory`. Буфер фиксированный: события старше 12 переходов вытесняются. Секреты и сетевые команды в нём не хранятся.

Windows Agent уже пересылает `/health` как JSON. Сервер при каждом авторизованном ESP32-отчёте сравнивает `seq` в рамках одной загрузки и записывает отдельные `FIRMWARE_GPIO_OFF` и `FIRMWARE_GPIO_ON` в существующий журнал. Дубли не появляются. При изменении `bootNonce` создаётся событие перезагрузки, а старые seq не переиспользуются. При пропущенных данных создаётся `FIRMWARE_HISTORY_OVERFLOW`, а неизвестные промежуточные события **не выдумываются**.

Экран `Тракт оповещения` показывает эти события с причиной и `uptimeMs`. Время на сервере является временем **наблюдения**, а не точной UTC-меткой физического контакта реле.

## Безопасность и границы

- Эта история фиксирует программное командное состояние GPIO13, а не измеренное напряжение на реле или акустическую слышимость.
- Все HMAC-проверки, fail-safe, heartbeat, lease и команда `powerOff()` остаются прежними. Изменения не включают усилитель и не разрешают МЧС-трансляцию.
- Новые поля появятся только после установки новой прошивки ESP32; GitHub Actions компилирует её, но не прошивает физическое устройство.
- При потере Wi-Fi новая история хранится только пока ESP32 работает; перезагрузка теряет буфер, это явно видно по новой загрузочной эпохе.
- Короткие перебои напряжения питания, не меняющие управляющий GPIO, этот журнал не обнаружит.

CI включает серверные проверки короткого OFF→ON между опросами, защиты от дублей, перезагрузки и потери событий из переполненного буфера; существующее отдельное PlatformIO-задание продолжает собирать ESP32.

**Для аппаратной диагностики:** обновление прошивки и контроль электрики проводить без подключённой сетевой нагрузки до проверки специалистом. Затем сравнивать серию событий ESP32 с `power-diagnostics.log` Windows Agent; случай `ON_COMMANDED` без физически подтверждённого напряжения не доказывает работоспособность AA-300.
