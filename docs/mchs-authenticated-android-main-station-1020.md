# PR #1020 — реальное принятие Android-события в очередь основного МЧС-эфира

## Обнаруженный блокирующий дефект
В `POST /api/safety-ingest/event` HMAC-подпись Android-моста проверялась успешно, но **каждое** поступившее уведомление записывалось в `SafetyMchsEvent` с `verified:false`. Следующий механизм `bindAndroidAlarmCandidates` требует `verified:true`; поэтому ни одна вновь поступающая запись не могла стать автоматическим заданием ALARM, даже если Android и Radio Worker были подключены и все три production-флага включены.

## Что меняется
После успешной проверки HMAC событие отмечается `verified:true` только если выполняются ранее существовавшие критерии допуска `assessMissileProvenance`:
- тип — **только** `MISSILE_DANGER` или `MISSILE_ALL_CLEAR`;
- регион — «Тульская область»;
- канал Android входит в настроенный `MCHS_MISSILE_TRUSTED_CHANNEL_IDS`;
- событие имеет уникальный `eventId` и временную метку не старше 120 секунд и не далее 30 секунд в будущем.

Важно: `verified:true` в этой цепочке означает **проверенное сообщение авторизованного Android-моста из настроенного канала**, но **не официальную аттестацию МЧС**. Ответ ingestion явно содержит `officiallyVerified:false`. Иное происхождение текста система не гарантирует.

Вновь принятая запись после коммита уведомляет существующий монитор; ждать следующий 15-секундный интервал обычно не нужно. Это **не** прямой запуск PCM из HTTP ingest: монитор по-прежнему атомарно сохраняет дедупликацию, подбирает назначенный аудиофайл, пропускает очередь через единоличное claim и внутренний Worker transport. Периодический опрос остаётся резервом. Повторные HMAC-запросы не меняют существующую запись и не инициируют двойное воспроизведение; за это отвечает уже существующая запись source+sourceEventId и ledger.

Поведение:
1. `MISSILE_DANGER` → назначенный ALARM, количество повторений из настроек → естественное завершение.
2. `MISSILE_ALL_CLEAR` → назначенный ALL-CLEAR, однократно → естественное завершение.
3. После окончания PCM Worker возвращается к обычному эфиру, отдельная команда STOP для естественного окончания не требуется.

## Оставшиеся условия запуска
Для **реальной** трансляции на `/radio/live` и через Windows Agent по-прежнему должны быть настроены:
- `MCHS_INGEST_ENABLED=true`, секрет HMAC для Android-моста и корректный список `MCHS_MISSILE_TRUSTED_CHANNEL_IDS`;
- привязки аудиофайлов для обоих событий, действующие файлы ALARM, нужные повторы;
- `MCHS_ANDROID_MAIN_STATION_DISPATCH_ENABLED=true` (API), `MCHS_MAIN_STATION_COORDINATOR_ENABLED=true` (API) и `RADIO_MCHS_STATION_COMMANDS_ENABLED=true` (Worker);
- текущий рабочий Windows Agent, настроенный ESP32 и контролируемая силовая цепь AA-300.

**PR не включает эти флаги автоматически** и не создаёт фиктивных событий. Нельзя самостоятельно генерировать сообщения, похожие на реальную ракетную опасность, в production Android intake. Для проверки используйте безопасно изолированный аудиовыход и наблюдайте **настоящее** следующее уведомление, не имитируя публичную тревогу.

## Ограничения
- Наличие HTTP 200, записи START или выдачи PCM не доказывает физическую слышимость в залах. Это требует отдельного аппаратного приёмочного испытания.
- При совпадении нового события с выполняющимся монитором обработка может быть отложена до очередного штатного опроса. Экстренная доставка не должна зависеть от гарантированной миллисекундной задержки.
- Если `MCHS_MISSILE_TRUSTED_CHANNEL_IDS` не настроен, сообщения **не допускаются** для автоматической очереди. Проверяйте это до включения production.
- При старом `verified:false` уже сохранённые исторические записи не повышаются в статусе автоматически и не переигрываются.
